# 2026-09-09 — member-client #159 (David V3) native parity: what mapped, what didn't

Samson asked to parity the mobile apps to member-client #159. It has two themes;
the native reality turned out narrower than the diff, plus one genuinely bigger
piece.

## Shipped both apps (kotlin bdedcfe / swift 6bfd1c4)

- **§2.3 Sex required.** The Setup wizard's Details step gated on a date of birth
  only, so the Sex select could be tabbed past and the column kept its
  `unspecified` default. `canContinue` for `.details` now also requires a real
  selection (`gender != null && != UNSPECIFIED`), and the field is relabelled
  "Sex" (was "Gender"). New unit test each side ("details requires a sex, not just
  a date"). The shared setup test `profile()` helper now seeds a real sex so the
  many load→submit-details tests still walk past the step.
- **§2.2 Email under sub-account names.** The Sub Accounts rows showed name (or
  email as fallback); they now show the email on its own line under the name (via
  `FamilyMember.hasName`), suppressed when the email is already the title.

## Already correct here — no change needed

#159's count repairs (§2.2 "Subaccounts · 2 of 3 used", drop the primary, drop the
"N Free" badge) fixed a member-client bug the native apps never had: both count
`family.size`/`family.count` (primary excluded) and show no Free badge. The
paid-unused-seat banner + `subaccountCapacity(included + purchased)` don't apply —
the native `Entitlement` has no `seatQuantity`/purchased-seats field (only
`includedSubaccounts`); additional seats aren't surfaced natively yet.

## Deferred — the headline gate swap (needs a decision)

§2.3–2.5's core is gating the run on the **enrollment ladder** (`myEnrollmentState`
→ `registrationOwed`/`outstandingSteps`) instead of `onboarding_completed_at`, and
assembling the run from what's owed (a returning canceled/expired member = a new
PIN only, "Step 1 of 1").

- The gateway field **exists** (introspected `gateway-dev`: `MemberEnrollmentState
  { status(MemberStatusRef), phoneVerified, hasAddress, hasSex, hasBirthday,
  pinSet, pinResetRequired }`), so a port is feasible AND verifiable.
- BUT the native onboarding **architecture diverges**: member-client has one
  `RegistrationScreen` gated by `needsRegistration`; the native apps show a
  post-login **ProfileCompletion checklist** (gated by `onboardingCompletedAt ||
  allDone`) with the multi-step **Setup wizard** as a separate flow. Swapping the
  gate touches the launch path and doesn't map 1:1.

So it's staged as its own focused PR (task #75), pending Samson's go-ahead, rather
than bundled into these two clean fixes. Note: the native gate already *derives*
partly (`allDone`), so it isn't as exposed to the flag-drift problem #159 fixes as
member-client's flag-only gate was.
