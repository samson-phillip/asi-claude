## What the schema says

```
notifyBySms   Boolean  "How this contact is alerted. Both default false: nothing
notifyByEmail Boolean   sends these alerts yet, so an unset field must not stand
                        in for consent to contact a third party."
```

That description is the C4 conversation coming back as documentation, and it
sets the rules for this screen:

- **Nothing pre-ticks.** Both start off.
- **Both are always sent, explicitly.** An omitted key would let the gateway's
  default stand in for a choice the member never made — the exact thing the
  warning is about. `false` is a value here, not an absence.

## Decisions

### A channel needs somewhere to send to

"Text message" is unavailable until a number exists, and says so in its own
label — *"Text message (add a number first)"* — rather than being silently
inert. If the address is cleared after ticking, the channel drops on the way
out. A stored "text them" with no number is a preference nobody could ever act
on, and this field is the record of who agreed to be contacted, so it has to
mean something.

### The caption says what is actually true

> Alerts aren't switched on yet. This records how they should be reached once
> they are.

Nothing sends these alerts. A member must not leave this screen believing
someone will be told. Collecting the preference is still worth doing — it is
real, it is stored, and it is ready — but not at the cost of implying a safety
net that does not exist.

### Ticks do not carry between contacts

`openContact()` clears them with the rest of the form. The next contact may be a
different person reachable a different way.

## The C4 fix was incomplete

Reworking the nudge left the same false promise in **five** other places. Found
while reading screen 16's copy for this work:

| Where | What it said |
|---|---|
| `CallScreen` (both platforms) | "Your emergency contacts have been alerted with your location." |
| Contact form subtitle (both) | "They're alerted with your location the moment you connect to an attorney." |
| Notification preview (Android) | "They're alerted with your location during any encounter." |

The call-screen one is the serious one. It is shown **while a member is
connecting to an attorney** — during a real encounter — and states as
accomplished fact that their contacts know where they are. Nobody has been told
anything. That is the worst thing on that screen to be wrong about, and it was
in the design verbatim, which is presumably why it survived the first pass.

Replaced with "Stay on the line — an attorney joins as soon as one is free."
The deviation from the reference is commented in place on both platforms so it
does not get "corrected" back.

**Worth generalising:** C4 was closed after fixing the instance that prompted
it. The lesson is that a copy defect is rarely in one place — the phrase should
have been grepped repo-wide the first time. It has been now.

## Screen 16 was unreachable

Profile → Emergency contacts → **"Manage"** opened the checklist. Contacts was
already ticked there, so the row had no way in, and a member with one contact
could never add a second. The row promised management and delivered a read-only
tick.

It opens the form directly now, and the "nothing left to do → go Home"
auto-skip no longer fires on someone who asked for the form — which is exactly
the member who has nothing left to do.

Same family as yesterday's readiness-row defect: a row that names one thing and
navigates somewhere else. Worth checking the remaining nav rows for it.

## An operational note

The machine ran out of disk entirely — zero bytes — partway through. Cause was
mine: iOS was being built into **two** DerivedData trees, the default one and a
second under the scratchpad passed via `-derivedDataPath`, so a day of builds
was stored twice. Nothing was lost, but no tool could run at all, since both
Bash and Write create a file before doing anything.

Fixed by clearing `~/Library/Developer/Xcode/DerivedData` (7.7G). **Use the
default DerivedData from now on** — the second tree bought nothing.
