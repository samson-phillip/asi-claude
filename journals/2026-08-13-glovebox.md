## The model, established before any code

`AdminDocumentField` carries a free-form `type` string, and the vocabulary on dev
turned out to be:

```
text  dropdown  file  image  agreement  policy  guide  form
example  "example 3"  "example 4"  "example 5"
```

The four Glovebox sections use only `text`, `dropdown` and `file`:

| Section | Fields |
|---|---|
| Driver's Information | Issuing State (dropdown, 6 options), Driver's License (file), Insurance Information (file) |
| Health Information | Health Conditions (text), RX Copies (file) |
| Gun Information | Gun Owner (dropdown, Yes/No), Gun Permit (file) |
| Citizenship Info | Passport (file), Birth Certificate or Visa (file) |

**The design shows richer field sets than exist** — "License number",
"Expiration", "Mental health conditions", "Permit number", "Visa number". Those
are admin-configured, not fixed by the design, so the screens render whatever
`adminDocumentFieldList` returns. When the backend adds a field it appears with no
code change. That is why 14A–14D is one screen and not four.

### The upload contract, proven live before building on it

```
requestUserDocumentUpload(userId, adminDocumentFieldsId, fileName, contentType, sizeBytes)
  → { uploadUrl, method, headers[{name,value}], expiresAt, s3Bucket, s3Key }
PUT the bytes to uploadUrl
createUserDocument(input: { userId, adminDocumentFieldsId, fileName, s3Bucket, s3Key, ... })
```

Verified by hand with curl first: ticket → `PUT` → `HTTP 200` → document id →
`userDocumentDownloadUrl` → **the exact bytes came back**. Worth doing before
writing a line of UI.

Two details worth keeping:

- **`sizeBytes` is a `String`** on the wire, despite being a byte count.
- **`headers` includes `Host` and `Content-Length`.** Those belong to the HTTP
  stack; setting them by hand either gets ignored or breaks the signature. Only
  `Content-Type` is ours to apply, and the live `PUT` returned 200 with just that.

## Decisions

**Sections are filtered by data, not by a hardcoded list of four codes.** A section
appears if it has at least one field the member fills in. That keeps the
organisation's own templates (Contract, Form, Guide, Policy, Incident Report) and
the dev test rows out, while letting a new section the backend adds show up on its
own — which is what the design's screen-13 note asks for.

**No delete control.** The design puts a `✕` on every document tile.
`deleteUserDocument` returns `forbidden` for a member on their own document, so a
delete button would always fail. Left out and raised as A5.

**The S3 `PUT` carries no bearer token.** The presigned URL *is* the credential;
attaching ours would hand a working session to a third party. Pinned by a test.

**A 15 MB cap on what we read into memory.** The bytes sit in RAM between the
picker and S3, so an unbounded read is a way to be killed while holding someone's
documents. The size is checked from the content provider *before* reading.

**A failed `PUT` never records a document.** Better a missing row than a Glovebox
row pointing at bytes that are not there.

**Leaving a section discards unsaved text edits.** They were never sent, and
keeping them would make a later screen show answers the server does not have.

**One file at a time.** A second upload is refused while one is in flight, and the
spinner is scoped to the field being uploaded rather than the whole screen.

**A file picker, not Camera/Gallery.** The design shows both. A document picker
covers photos *and* PDFs — which the design's own copy asks for ("Insurance card,
medication list, PDF or photo") — and camera capture is still owed.

## A bug found by looking at a device

The section list rendered **five** sections: the four Glovebox ones and
**"Policy"**.

I had mapped `image` → file upload, on the reasonable-looking assumption that an
image field is an upload. The only `image` field on dev is called "Example" and
belongs to the organisation's Policy template — so that one guess dragged an org
document template into the member's personal Glovebox.

`image` is now treated as unknown, and the backend has been asked what the `type`
vocabulary actually means (A6). Every unit test passed while this was wrong; it was
only visible on screen.

The general lesson is the one this project keeps teaching: **a plausible mapping is
still a guess, and guesses belong in the backend doc, not in the code.**

## Test results

| Suite | Result |
|---|---|
| Android unit | **226 pass**, 0 fail (was 205) |
| iOS unit | **221 pass**, 0 fail (was 202) |

Coverage: section filtering (org templates and test rows excluded), field-type
mapping including the `image` regression, filled counts from either a value or a
file, dirty-checking and trimming, discarding edits on leaving, the three-step
upload, no bearer token on the S3 `PUT`, `Host`/`Content-Length` stripped, a failed
`PUT` recording nothing, one-at-a-time, and file-size formatting.

**Two of my own test-harness bugs, not product bugs:**

1. The stub matcher keyed on bare operation names, and `"DocumentFields"` is a
   substring of the variable `adminDocumentFieldsId` — so save and upload calls
   matched the *fields* stub. Nine tests failed for the wrong reason. Keys now
   include the `query`/`mutation` keyword.
2. `RecordedRequest.body` is a one-shot buffer and the matcher has to read it to
   choose a stub, so an assertion reading it again saw an empty body. Bodies are
   now captured at dispatch time.

## Open issues / next steps

1. **The iOS file *read* is unverified on a device.** The importer presents
   correctly, but a clean simulator has no documents to pick, and seeding one is
   not representative (`simctl addmedia` takes images only). So `fileImporter`
   presenting is confirmed; `readPickedFile` reading bytes from a security-scoped
   URL is covered by unit tests and by parity with the verified Android path, not
   by a real pick. Worth one manual pick on a real iPhone.
2. **`deleteUserDocument` is `forbidden`** for a member's own file (A5), so there
   is no `✕`. Two test files of mine are stuck on the test account as a result.
3. **Camera capture is not built.** The design shows [Camera] [Gallery]; we have a
   document picker. Mine to do.
4. **No masking of sensitive values.** Screen 14A masks a licence number
   (`•••• •••• 4821`). No such field exists in the data yet; when one arrives it
   should be masked rather than shown.
5. **Documents are not viewable in-app** — "Open" hands the presigned URL to the
   browser. Building a viewer is a bigger job and pretending to preview a PDF we
   cannot render would be worse.
6. **Section icons are not loaded.** Three of the four hold CloudFront URLs; with
   no image loader wired they fall back to a neutral glyph. Same gap as the
   incident tiles.
